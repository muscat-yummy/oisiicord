# Security policy

This is an unaudited application. Do not describe it as Proton-equivalent or as offering a guarantee against a malicious application distributor.

## Reporting

Report vulnerabilities privately using GitHub's private vulnerability reporting when enabled. Do not put private keys, session cookies, passwords, or real conversation data in public issues. Until private reporting is enabled, request a private contact from the repository owner without posting exploit details.

## Threat model

The client encrypts message text, reply identifiers, edits, reactions, pins, and file metadata before transmission. The application database stores encrypted envelopes, encrypted private-key vaults, public identity keys, and authentication verifiers. The server does not receive the password, the vault decryption key, a plaintext message, or a plaintext attachment through the implemented application protocol.

The server can see usernames, display names, guild/channel names, types, topics, default channels and administrative audit entries, membership, requests, timestamps, ciphertext lengths, IP addresses while connected, typing events, and voice room participation. Profile biographies, pronouns, status, banner colors, server descriptions, roles, categories, emoji descriptors and rule acceptance are application metadata. Rule message bodies remain encrypted. Profile/server icons are cropped to 128×128 WebP and encrypted before uploading through the file adapter. Their decryption descriptors are intentionally shared as profile metadata, so these public images do not have conversation confidentiality. Clients only display decoded 128×128 WebP images and do not render supplied SVG/HTML. The attachment proxy sees encrypted bytes and file IDs; end2end.tech sees the proxy IP, upload size and timing. A downloaded encrypted attachment is accessible to anyone possessing its external file ID; plaintext additionally requires its random encryption key. File IDs and keys are carried inside encrypted messages.

## Protocol v1

- Identity: independent ECDSA P-256 signing and ECDH P-256 encryption key pairs, generated on the client with Web Crypto.
- Password processing: PBKDF2-HMAC-SHA-256, 600,000 iterations, random 256-bit account salt, separate application/version/purpose labels for authentication and vault keys. This is not SRP or OPAQUE. The server receives the derived authentication secret and stores an Argon2id verifier (64 MiB, three iterations). Do not reuse derived authentication secrets across services.
- Vault: AES-256-GCM, random 96-bit nonce, username and protocol version as authenticated context. Server-side password recovery cannot recover this vault.
- Each message/event: independent 256-bit content key and 96-bit nonce; AES-GCM authenticated context includes the complete canonical header (ID, room, author, membership version, timestamp, ephemeral public key).
- Key envelopes: a fresh ECDH ephemeral key pair per event; ephemeral/private-to-recipient/public ECDH, then HKDF-SHA-256 with a versioned salt and header/recipient context, then AES-GCM wrapping of the content key. Each current member receives a separate key envelope.
- Authenticity: ECDSA-SHA-256 signature over canonical JSON for the entire header, recipient envelopes, and encrypted payload. Context and signatures are checked before rendering.
- Guild membership: the owner signs a versioned complete member list, including the exact identity keys. Recipients validate this signature. Historical member-list signatures are retained to authenticate older messages. The server requires current membership/version on each new event. An owner may create multiple guilds; each account can belong to at most 30 guilds in total. Automatic admission uses an owner-signed invite capability and a participant-bound proof; clients verify both before accepting supplemental members.
- Trust: public keys are pinned in browser localStorage on first use (TOFU). Invite links contain the owner's public keys in the URL fragment. Users can compare SHA-256 fingerprints over another communication channel and mark them as verified. A changed pinned identity blocks sending. Guild IDs are pinned to owner identities, and DM IDs are pinned to their two participant identities, so replacing the whole signed directory with a different owner/peer is also rejected in an existing trust state. A per-browser maximum membership version detects a lower current roster version.
- Files: random AES-256-GCM key/nonce per file; encrypt before `POST /upload`; store only a random `.enc` filename externally. The file name, MIME, size, hash, encryption key/nonce, file ID and deletion secret travel inside the signed encrypted message. SHA-256 and GCM authentication are checked before saving plaintext to disk. No automatic remote resource previews or HTML rendering.
- Voice/video/screen: browser WebRTC DTLS-SRTP, peer-to-peer mesh, up to six connections. SDP and ICE are signed and encrypted using the same identity/envelope mechanism. The service does not terminate the media encryption. A TURN relay may carry encrypted media. ICE reveals participant IPs to peers and configured STUN/TURN operators.

## Explicit limitations

- No independent cryptographic/security audit; no Proton code or Proton key transparency infrastructure is integrated.
- No public append-only key transparency log, cross-device consistency proof, transparency gossip or authenticated account directory. TOFU does not stop first-contact key substitution; compare fingerprints and invite-owner keys independently.
- No Double Ratchet, MLS, post-compromise security or forward secrecy for stored messages. Long-term recipient key compromise can expose historical envelopes. The ephemeral sender key alone does not provide recipient-compromise forward secrecy.
- The server that serves this web client can replace JavaScript and capture keys/passwords on a later visit. CSP protects against some injection, not a malicious origin. For a stronger distribution boundary, ship independently signed native clients with reproducible builds and verified updates.
- A compromised endpoint/browser extension, XSS in trusted code, malware, screenshots, or an authorized recipient can expose plaintext. localStorage pins can be cleared or tampered with by code controlling that origin/device. New browsers have a fresh TOFU trust state.
- No cryptographic global ordering/completeness guarantee. A malicious server can suppress, delay, reorder, or replay historical valid events in a new browser. IDs are deduplicated in the current client history; signatures do not prove that the server delivered everything.
- Deletion/editing publishes a signed encrypted event; previously delivered ciphertext and recipient copies remain. Deleted external files may remain in upstream backups. Deletion secrets are visible to conversation recipients after decryption.
- New invitations intentionally grant access to historical conversations. The owner encrypts original event content keys into an authenticated invite snapshot. Active invitations receive additional event-key boxes, inside each signed envelope, so a new participant can read messages sent after link creation even if the owner is offline. Invite private material stays in the URL fragment and client; saved history credentials are encrypted only to the joining participant. Removed members retain old messages and keys; roster consolidation revokes old invite capabilities and future events omit removed members and revoked invite boxes.
- Browser sessions expire in seven days. Password login unlocks the vault; remembered browser sessions restore the non-extractable keys described below. There is no password reset, passkey/2FA, independent device-key revocation, or automatic trust synchronization in this version. Password changes re-encrypt the existing identity vault and invalidate other sessions; they do not rotate identity keys. Authenticated users can view and revoke their other sessions.
- Search runs in decrypted client history. At most 10,000 events are loaded per synchronization call; additional events can be requested using the explicit history continuation control. There is no server plaintext search or content moderation pipeline.
- Rate limits apply to a single process and do not provide full denial-of-service protection. Add connection/IP/rate controls and request timeouts at the reverse proxy. Keep one Bun process for this SQLite deployment; horizontal scaling needs shared fanout and coordinated limits.

## Deployment

Use a dedicated HTTPS origin, a patched Bun runtime, strict control over who can modify deployed assets, and restricted access to SQLite plus backups. Do not terminate HTTPS on an untrusted host. Keep `APP_ORIGIN` exactly equal to the browser origin. Bind Bun to loopback behind the TLS reverse proxy. Cookie authentication uses HttpOnly, SameSite=Strict, and the Secure/__Host- attributes on HTTPS. State-changing HTTP and WebSocket handshakes require an exact Origin match. SQL uses prepared statements. Static serving is an explicit allowlist. Request sizes, session lifetime, and rates are bounded. The application does not trust forwarded IP headers.

Invite revocation via the HTTP API is an application authorization decision. A malicious server colluding with a revoked bearer can attempt to backdate admission under the same signed roster base. An owner-signed roster update advances that base and invalidates the old capability cryptographically; member removal performs this consolidation. Invite snapshots and links grant conversation-history access to their recipients and should be treated as access credentials.

History-key recipients are bound to the guild ID and owner-signed roster base. Clients remember the highest owner-signed base seen on that browser; a larger unsigned membership index cannot replace it with an older signed base. This local trust does not establish freshness on a new browser or device.

## Remembered browser login

After a successful password login, the browser stores non-extractable ECDSA/ECDH CryptoKey objects in IndexedDB. Passwords, authentication secrets, plaintext PKCS#8 keys, and vault decryption keys are not persisted. Restoration requires both the existing HttpOnly session cookie and the matching stored session identifier, user ID, public keys, and expiry. The authenticated session endpoint returns only public identity data, salt, the encrypted vault, and non-authenticating session metadata. Logout removes the local keys and revokes the server session; other open tabs receive the logout. Sessions still expire after seven days. Browser data removal requires another password login.

A remembered login lets anyone with access to the unlocked browser profile use that account. Non-extractable keys prevent the exportKey API from exporting them, but do not protect against compromised same-origin JavaScript or access to the browser profile. The existing malicious-server/client-delivery limitations continue to apply.

## Developer rendering and media previews

Mermaid and syntax highlighting assets are served from pinned local packages. Message source is never sent to a remote renderer. Mermaid runs in an opaque-origin sandboxed iframe without `allow-same-origin`; its CSP blocks network connections and external media. The parent validates the message source window, sanitizes returned SVG, and uses another opaque sandboxed viewer. Diagram directives/frontmatter cannot change renderer configuration; strict mode disables callbacks and HTML labels. The main application CSP is unchanged. Public vendor modules alone allow cross-origin loading for these sandboxed frames. They do not expose application data or arbitrary package paths. Diagram caches are cleared on logout.

Attachment previews fetch ciphertext using the existing file proxy, verify the signed descriptor's hash and AES-GCM authentication, check plaintext size and media signature, and only then create a local Blob URL. Inline images are limited to the supported raster formats and 32 megapixels; SVG attachments remain download-only. Video and audio codecs depend on the browser. Preview cache space is bounded, inactive objects can be evicted, and logout revokes Blob URLs and aborts pending loads. No remote URL preview or autoplay is introduced.

Voice signaling accepts only signed signal envelopes, excludes invitation history-key boxes, and is never stored as a chat event. Chat submission rejects signal envelopes. Both paths retain identity, room, membership-version and recipient validation.

## Departure, blocking and account deletion

A member can publish a signed departure scoped to the guild and owner-signed roster base. The current certificate carries ordered admission/departure operations, while historical certificates retain the membership needed to authenticate old messages. Clients verify departing members against the membership at that point in the sequence, reject owner departures and repeated departure nonces, and pin previously observed departure nonces per roster base. Inflating an unsigned membership version cannot erase an already observed departure on that browser. As with the existing directory, an origin can suppress updates before a client has observed them; this is not a global ordering or transparency proof.

Departure removes room access, roles and saved server-side history credentials and revokes existing invite capabilities. Future event boxes omit the departed member and old invite secrets. A fresh owner-signed invite can permit rejoining after departure. Old valid admissions cannot be replayed after the departure cutoff, and owner-signed roster consolidation clears the operation history under a new authenticated base. Prior recipients retain plaintext and historical keys they already obtained.

Blocks are account-scoped server metadata. Either side of a blocked DM is denied new messages and voice signaling; historical DM access remains. Shared guild delivery still includes authorized guild members, so blocking collapses content and suppresses notifications in the client, rather than promising cryptographic secrecy from another authorized guild member. Blocked voice peers are excluded from signaling delivery and clients close existing peer connections when the directory changes.

Account deletion requires the current authentication secret and an identity-signed deletion request covering the complete owned-guild list and signed departures. The transaction rechecks the account verifier and memberships after asynchronous verification. Owned guilds are deleted only when their complete list is explicitly covered; the client separately confirms their deletion. All sessions, profile data, vault, salt/auth verifier, requests, private history credentials and block rows are removed or overwritten. The deleted user row retains a random replacement username, a deleted display label, ID and public keys so historical signatures, DM relations and administrative history remain verifiable. Delivered ciphertext, recipient copies, administrative records and existing backups are not retroactively erased. Connected clients discard account-local browser data on account deletion; offline copies on other devices cannot be remotely wiped.

The live file-adapter command uses one synthetic 128-byte input, sends only its authenticated ciphertext, verifies a downloaded copy and deletes the uploaded object. It logs stage booleans, not file IDs, deletion passwords, session cookies or private keys. Provider JSON success, byte limits, fixed-origin requests, timeouts and redirect rejection are enforced by the adapter. HTTP 200 error bodies are not treated as successful deletion.
